# Local setup gate

1. Confirm a local Codex execution environment on the user's intended machine. A hosted OAuth connection or browser session is not proof of local readiness. Respect sandbox and repository access rules; do not start/restart user-managed services as setup convenience.
2. Check `node --version` (18+) and `supaflow --version` (0.8.0+). If missing/outdated, explain the prerequisite and offer `npm install -g @getsupaflow/cli`; execute installation only after explicit approval. Never install or upgrade Node automatically.
3. The package's read-only helper can run as `node <plugin-root>/scripts/check-setup.mjs`; resolve the installed plugin root rather than assuming the current directory is the package. Add `--agent` only for an agent request. It prints sanitized readiness flags, never auth payloads, IDs, or command stderr. Failure means resolve that gate before operations, not bypass it. It does not install, log in, select a workspace, start Docker, or validate stored credentials remotely.
4. Check local `auth_status` (or `supaflow auth status --json`). `authenticated` means credentials are configured, not that a remote request has succeeded. If false, ask the user to run `supaflow auth login` in their own terminal. CLI 0.8.0+ opens browser OAuth with PKCE; the user signs in, reviews the requesting app, organization, permissions, and return destination, and authorizes access in the browser. Never accept a key or token in conversation. Do not configure an API key as the default setup path.
5. List accessible workspaces using the local server or `supaflow workspaces list --json`. This also checks remote access. Stop on authorization failures. Verify the selected workspace is accessible and matches the request. When none is selected or multiple are plausible, ask the user to choose; change the CLI selected workspace only for that choice, then reread status. Local selection affects future calls and is separate from hosted `workspace_id` arguments.
6. Before an agent operation, check Docker client/daemon availability without starting either. If inaccessible, ask the user to resolve it. Require the exact local capability, especially `agent_upgrade` or `jobs_cancel`. An older already-running MCP process may not expose newly installed CLI features: explain that a fresh local session may be needed; do not restart services automatically.
7. Resume only after the relevant checks pass. For coexistence with an old manual `supaflow-local` registration, have the user choose which registration to keep; never silently delete one, import hosted credentials, or change global approval settings.

No hook is required: these checks apply whenever the entry or domain skills are used, even when the host did not run setup automatically.


## Authentication choices and compatibility

- Browser OAuth is the default for interactive `supaflow auth login`. The CLI stores credentials locally and refreshes access tokens automatically. Local stdio MCP inherits this same CLI login; never put OAuth tokens in `mcp.json` or copy a hosted MCP grant into the CLI.
- API keys remain an option for headless/CI use or when explicitly chosen by the user. Have the user configure `SUPAFLOW_API_KEY` through their secret manager or own terminal; never request the value. An environment API key takes precedence over stored OAuth, so check the reported auth method/source when diagnosing an unexpected account. Do not print the environment or credential file.
- Existing API-key logins remain valid. Do not force migration or log out a working user. New browser login replaces a stored API key; API-key login replaces stored OAuth. Do not remove either without the user's intent.
- `auth_status.method` (or CLI JSON `method`) is `oauth` or `api_key` on the updated CLI. Older releases can omit this field: use `authenticated` plus a successful workspace list, not a key-presence check. If login prompts for a key, that CLI lacks the browser-login default; explain the version mismatch and offer an approved upgrade to CLI 0.8.0 or newer.
- Never expose or invoke login as an MCP tool, approve browser consent on the user's behalf, or silently fall back to API keys after OAuth failure. Recheck local auth status and accessible workspaces after the user's login. Hosted connector OAuth remains a separate login.
